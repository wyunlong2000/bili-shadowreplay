## 1. 评审摘要

**决策 `DEC-001`：以 BSR 现有抖音录制器作为唯一监测入口。**监测、开播事件、录制和后续自动化沿用同一条后端链路，不部署独立监测器，也不替换现有录制器。

候选切片、分析进度和通知同样复用现有组件：切片走既有任务与 `clip.generated` Webhook 链路，分析进度沿用 `record_summaries` 的状态与恢复模式，评分复用既有弹幕密度分析。

方案吸收三个参考项目的设计思路：借鉴 `washls/douyin-live-monitor` 的未知状态、限流退避与连续异常熔断；借鉴 `nfe-w/aio-dynamic-push` 的状态基线和提醒去重；借鉴 `ihmily/DouyinLiveRecorder` 的长时间值守经验。外部项目不作为运行依赖，代码复用须另行审查许可证。

本文件定义业务边界、方案决策、需求和验收条件。评审通过后，先编写 `DDES-001` 开发详设，再进入代码开发。

## 2. 目标与范围

目标流程：

> 监测开播 → 自动录制 → 录制期间分析高光 → 生成候选切片 → 邮件提醒 → 人工检查并发布

第一阶段以一个抖音主播跑通全流程；实现放在 Rust 后端，使桌面版与 Docker 部署共用。抖音投稿保持人工操作，不接入自动发布。

本方案不新增独立的抖音轮询服务，不替换 BSR 的账号、签名、直播流解析和录制实现，也不承诺 AI 评分能预测作品热度。

## 4. 方案比较与决策

| 方案编号 | 做法 | 结论 | 原因 |
| --- | --- | --- | --- |
| `ALT-001` | 扩展 BSR 现有抖音监测与录制链路 | 选用，见 `DEC-001` | 已有抖音接口、账号 Cookie、签名、流解析、录制及 `LiveStart` 事件；自动化可直接消费已有事件。 |
| `ALT-002` | 在 BSR 旁运行独立监测器，再通知录制器 | 不选 | 形成两套主播状态和轮询任务；开播判定、重试和去重需跨进程同步。 |
| `ALT-003` | 将 BSR 监测或录制替换为外部项目 | 不选 | 外部录制器不能直接复用 BSR 的直播会话、弹幕、录播缓存和切片任务；需增加适配维护面。 |

### `DEC-001` BSR 原生监测链路

- 普通监测沿用现有 Webcast 主接口和 H5 回退，不在每次正常轮询中无条件请求全部来源。
- 对未知、冲突或连续失败，可按退避策略重试；是否增加周期性完整巡检由详设根据请求成本确定。
- 开播由现有生命周期产生 `LiveStart`；分析任务订阅该事件，不再建立一套开播监测循环。
- 候选切片复用既有自动整场切片的任务与 `clip.generated` Webhook 链路；增量分析进度沿用 `record_summaries` 的持久化与恢复模式。参见 `REF-009` 至 `REF-011`。
- 分析任务以记录行和 `parent_id` 为场次键挂载；平台场次标识在 LiveStart 时可能为空，不阻塞任务创建。参见 `REF-014`。
- 外部项目仅提供设计参考。`washls/douyin-live-monitor` 当前采用 PolyForm Noncommercial 1.0.0，方案禁止直接复制其代码；其他代码复用也须保留 MIT 声明并单独审查。

## 6. 开播状态与轮询规则

### 6.1 状态转换

| 当前确认状态 | 本次结果 | 处理 |
| --- | --- | --- |
| 未确认 | `UNKNOWN` | 记录错误并重试；不发开播或下播事件。 |
| 未确认 | `OFFLINE` | 记录检测结果并进入未开播状态；不创建录制或分析任务。 |
| 未确认 | `LIVE` | 建立直播场次，发出一次开播事件并启动录制。 |
| 未开播 | `OFFLINE` | 更新最近检测信息；不创建录制或分析任务。 |
| 未开播 | `LIVE` | 建立直播场次，发出一次开播事件并启动录制。 |
| 开播中 | `UNKNOWN` | 保留开播确认状态；不发下播事件，不因监测失败主动结束录制。 |
| 开播中 | `LIVE` | 更新直播间元数据；不重复启动场次任务。 |
| 开播中 | `OFFLINE` | 确认场次结束，结束录制并进入收尾流程。 |

主播首次检测即为 `LIVE` 时，录制必须启动。状态基线用于抑制重复事件，不得把已开播主播当作无需处理的初始状态。

### 6.2 轮询、退避和限流

- 基础间隔默认 30 秒，带随机抖动；用户可配置更长间隔。抖音低于 30 秒的配置是否允许是 `RVW-001`。
- 退避建议从基础间隔开始逐次加倍，上限暂定 5 分钟，并加入随机抖动；`Retry-After` 存在时遵循服务端时间。上限是待评审参数 `RVW-002`。启动阶段的失败可先按 10、30、60 秒的短序列重试，再进入常规退避（参考 `EXT-001`）。
- 普通网络错误、无法解析的响应，以及同轮多来源结果冲突，均归为 `UNKNOWN`；冲突不得改变确认状态。明确限流应设置抖音平台冷却时间。单主播错误不应阻塞其他平台任务。
- 任一明确成功结果恢复基础间隔并清除连续未知计数。检测状态与录制流状态分别维护。
- 连续异常达到阈值后暂停该主播检测并只通知一次；账号恢复或用户重新启用后恢复检测。阈值是待评审参数 `RVW-005`。退避期间用户主动查看主播是否强制探测一次是 `RVW-006`。

## 7. 自动化流程与模块边界

1. `FLOW-001` 用户添加抖音主播、配置账号并启用自动录制。
2. `FLOW-002` 现有录制器轮询状态；明确开播时发出 `LiveStart` 并启动录制。
3. `FLOW-003` 后台分析任务读取稳定落盘窗口（已完成 segment 前缀，排除正在写入的末段）、弹幕和增量字幕，保存检查位置。
4. `FLOW-004` 评分任务合并相邻候选区间，补足前后文并按唯一键去重。
5. `FLOW-005` 现有 FFmpeg 流程生成候选切片，与自动整场切片共用任务和产物记录链路；切片范围排除正在写入的末段，生成时机见 `RVW-007`；记录产物和失败状态。
6. `FLOW-006` 切片生成事件（`clip.generated`）进入 Webhook 邮件服务；传输失败沿用既有重试，业务层按候选唯一键去重，不重复生成切片。
7. `FLOW-007` 用户查看候选后在抖音客户端人工发布。

| 模块编号 | 职责 |
| --- | --- |
| `MOD-001` | 复用 `DouyinRecorder` 和通用录制生命周期；维护检测状态、退避和运行状态。 |
| `MOD-002` | 后台增量分析、候选评分和持久化进度；沿用 `record_summaries` 的状态与恢复模式；异常不阻断录制。 |
| `MOD-003` | 调用现有 FFmpeg 切片能力，含自动整场切片的任务链路；保存候选产物和任务状态。 |
| `MOD-004` | 复用 Webhook 事件与传输层重试，由外部邮件服务发送；管理通知的业务幂等键。 |
| `MOD-005` | 展示主播检测状态（含未知、退避和最近错误）、自动化任务状态、候选评分和切片链接；候选状态枚举沿用 `record_summaries` 的 status/stage 模式。 |
| `MOD-006` | 桌面版和 Docker headless/Web 共用后端流程；邮件链接复用现有 `/output`、`/cache` 静态路由（`REF-017`），受部署环境访问控制约束。 |

## 8. 高光候选评分

评分用于候选排序和过滤，不承诺预测作品热度。初期先使用弹幕和字幕；模型支持图像输入时再启用抽帧评分。

弹幕密度窗口分析已有实现（`REF-012`），`SCORE-001` 在其上叠加相对直播基线的对比与突增判定。评分所需 LLM 未配置时降级为弹幕与片段质量评分（`SCORE-001`、`SCORE-004`），不阻断流程。

- `SCORE-001` **弹幕热度**：数量、单位时间密度及相对当前直播基线的突增。
- `SCORE-002` **语音内容**：主题、事件完整性和脱离上下文后的可理解程度。
- `SCORE-003` **画面信息**：抽样帧可识别的动作、场景变化或关键画面。
- `SCORE-004` **片段质量**：起止完整性、前文依赖程度和与已有候选的重复度。

## 9. 数据、去重与通知

- `DATA-001` 候选记录至少包含主播、直播场次、起止时间、总分、评分信号、推荐理由、切片任务、通知状态和错误信息。
- `DATA-002` 候选切片唯一键至少由主播、直播场次和时间范围组成，用于切片及邮件通知的业务幂等；Webhook payload 携带该唯一键，传输层已有重试（`REF-013`），业务层不得重复发送。
- `DATA-003` 直播场次事件使用稳定去重键，复用现有 `records.parent_id`（`REF-014`）。平台场次标识在 LiveStart 时可能为空（抖音在录制启动后才有值），分析任务挂 RecordStart 及记录行而非 LiveStart；详设明确本地场次键及重启恢复规则。
- `DATA-004` 检测记录保存最近成功时间、最近错误类别、连续未知次数和下一次重试时间；敏感 Cookie 不写入日志或邮件。

邮件链接必须能从预期收件端访问，并受部署环境访问控制约束。项目没有内置网页登录认证，远程部署应使用 VPN 或带认证的反向代理。

## 11. 验收标准与追踪关系

| 验收编号 | 可验证结果 | 覆盖需求 |
| --- | --- | --- |
| `AC-001` | 配置主播开播后自动开始录制；应用启动时主播已开播也能开始录制。 | `REQ-001`、`REQ-006` |
| `AC-002` | 查询失败或限流时显示未知/错误及重试信息，不错误结束直播或录制；连续异常达到阈值后暂停检测并只通知一次。 | `REQ-002`、`REQ-005`、`REQ-007` |
| `AC-003` | 监测使用主接口及条件回退；请求间隔和退避符合评审确认的参数。 | `REQ-003`、`REQ-004`、`REQ-005` |
| `AC-004` | 同一直播场次最多创建一次开播自动化任务；重启恢复后不重复创建任务。 | `REQ-006` |
| `AC-005` | 分析只处理稳定窗口；重启后可续跑且不重复生成候选。 | `REQ-008`、`REQ-009` |

## 12. 风险与待评审项

- `RISK-001` 抖音网页接口、Cookie 和签名可能变化；应显示账号失效或接口异常并可恢复。
- `RISK-002` 轮询过频会增加限流风险；30 秒下限和 5 分钟退避上限需用真实主播验证。
- `RISK-003` 平台没有确认开播推送事件时，开播发现延迟受轮询间隔影响；短暂开播/下播可能落在两次轮询之间。
- `RISK-004` 平台场次 ID 在开播事件产生时可能为空（抖音到录制启动后才可用）；用 `records.parent_id` 兜底，详设明确事件与任务的挂载时机。
- `RISK-005` 增量分析增加 CPU、磁盘和模型成本；需限制分析频率、抽帧数量和单场切片数，云端字幕调用计入上限。
- `RISK-006` 邮件中的视频链接直接指向现有 `/output`、`/cache` 路由；这两个路径无认证，需考虑 Docker 媒体卷、网络可达性，远程部署应使用 VPN 或带认证的反向代理。
- `RISK-007` 自动录制、剪辑和传播应具备内容使用权限并遵守平台规则。

| 待评审编号 | 需确认事项 | 建议 |
| --- | --- | --- |
| `RVW-001` | 抖音轮询是否设置 30 秒硬下限？ | 建议确认；当前全局配置在小间隔下仍可能以 10–20 秒执行。 |
| `RVW-002` | 连续未知状态的退避上限是否为 5 分钟？ | 作为详设初始值，结合请求限制和可接受发现延迟验证。 |
| `RVW-003` | 启动时已开播是否发送用户通知？ | 建议启动录制并建立场次；通知和自动化任务按场次去重。 |
| `RVW-004` | 外部开源代码是否需要复制？ | 当前方案不要求复制；若后续需要，先审核许可证、来源声明和维护成本。 |
| `RVW-005` | 连续异常熔断：多少次后暂停该主播检测并只通知一次？ | 建议 10 次，参考 `EXT-001`；账号失效与普通网络错误是否区分阈值由详设确定。 |
| `RVW-006` | 退避期间用户主动查看主播是否强制探测一次？ | 建议允许但限频，防止退避被绕过导致限流加剧。 |
| `RVW-007` | 候选切片在直播中增量生成还是直播结束后统一生成？ | 建议第一阶段直播结束后统一生成：分析在直播中完成，切片避开末段不完整和与录制争抢资源；直播中增量切片作为后续优化评估。 |
| `RVW-008` | 增量字幕的后端与窗口粒度？ | 建议窗口 5–10 分钟；本地 Whisper 使用长驻实例避免重复加载模型，云端后端按窗口调用并计入成本上限。 |
