## 1. 目标与范围

基于 BiliBili ShadowReplay，为指定抖音主播提供以下自动化流程：

> 监测开播 → 自动录制 → 录制中分析高光 → 生成候选切片 → 邮件提醒 → 人工检查并发布

第一阶段聚焦抖音和单主播流程，不自动发布抖音作品。后续可扩展到更多主播、平台、评分策略和通知渠道。

## 2. 现有基础与需求差距

| 基础编号 | 现有能力 | 需求编号及待补工作 |
| --- | --- | --- |
| `BASE-001` | 已有抖音录制器；启用直播间后会自动监测并开录。添加抖音直播间需要账号及主播标识。 | `REQ-001`：验证目标主播的账号、标识和长时间录制稳定性；补充重试和状态提示。 |
| `BASE-002` | 录制内容以 HLS 播放列表缓存，后端已有按时间范围调用 FFmpeg 切片的能力。 | `REQ-002`：只分析已经写入完成的片段；持久化分析进度，避免重启后重复处理。 |
| `BASE-003` | 有 Whisper 字幕、弹幕密度高峰分析、画面抽帧和 LLM 助手；现有自动整场处理在直播结束后触发。 | `REQ-003`：新增录制期间的滚动分析及候选评分流水线。现有工具主要供交互式使用，并非自动选片服务。 |
| `BASE-004` | 后端已有后台任务、进度和事件通知机制。 | `REQ-004`：将分析、切片、通知接入后台任务，记录候选片段状态及失败原因。 |
| `BASE-005` | 现有投稿流程只支持 B 站；切片完成后已有 Webhook 事件，项目没有内置邮件发送。 | `REQ-005`：投稿由用户手动完成；第一阶段复用 Webhook 接入邮件服务，不增加抖音投稿接口。 |

## 3. 目标流程

1. `FLOW-001`：用户添加抖音主播，配置抖音账号并启用自动录制。
2. `FLOW-002`：后端监测开播并启动录制；下播后收尾并保存录播。
3. `FLOW-003`：录制期间按可配置的时间窗口处理已稳定落盘的片段，不读取正在写入的末尾片段。
4. `FLOW-004`：先用弹幕密度变化筛选候选时间段，再结合增量语音转写和可用的画面抽帧评估内容。
5. `FLOW-005`：合并相邻候选区间、补足前后文并去重，通过现有 FFmpeg 流程生成切片。
6. `FLOW-006`：切片完成后发送邮件，包含主播、直播时间、切片时间点、评分、推荐理由和视频访问链接。
7. `FLOW-007`：用户检查切片和发布信息后，手动上传到抖音。

分析频率、切片时长、候选阈值和每场直播的切片上限应可配置。初期可只启用弹幕和字幕信号；只有在所选模型支持图像输入时，才使用抽帧结果辅助评分。

## 4. AI 候选评分

评分用于排序和过滤候选片段，不承诺预测作品热度。建议结合可解释的信号，而不是让模型直接分析整场视频：

- `SCORE-001` **弹幕热度**：弹幕数量、单位时间密度及相对当前直播基线的突增。
- `SCORE-002` **语音内容**：字幕中的主题、事件完整性和可独立理解程度。
- `SCORE-003` **画面信息**：抽样帧中可识别的动作、场景变化或关键画面；模型不支持图像时跳过该项。
- `SCORE-004` **片段质量**：起止是否完整、是否依赖过多前文、是否与已生成候选重复。

模型调用失败不应中断直播录制；相关候选应保留待重试或标记失败。

## 5. 模块设计

- `MOD-001` **主播监测与录制**：复用现有抖音平台实现和直播间启用状态；网络错误、账号失效和平台接口变化应有可见状态及重试策略。
- `MOD-002` **高光分析任务**：由 Rust 后端后台运行，消费稳定的视频片段、弹幕和转写结果；保存处理位置及候选记录，实现幂等处理。
- `MOD-003` **候选切片生成**：复用现有时间区间切片和 FFmpeg 任务；单个候选失败不影响录制及其他候选。
- `MOD-004` **通知适配**：第一阶段复用 `clip.generated` Webhook 事件，由外部邮件服务发送通知；邮件发送失败可重试，且不应重复生成视频。
- `MOD-005` **前端配置和查看**：提供主播自动录制开关、分析参数、任务状态和候选切片链接；人工发布在抖音客户端完成。
- `MOD-006` **部署方式**：自动化逻辑放在 Rust 后端，使桌面版和 Docker headless/Web 部署共用同一套任务流程。

## 6. 候选数据与去重

- `DATA-001`：每个候选至少记录主播、直播标识、时间范围、总分及评分信号、推荐理由、切片任务标识、通知状态和错误信息。
- `DATA-002`：候选应有稳定唯一键，避免同一直播时间范围重复切片或重复通知。

## 7. 分阶段实施

### `PH-001` 抖音录制验证

- 选择一个主播完成账号配置、直播间添加和自动录制。
- 验证开播检测延迟、长时间录制、断网恢复、下播收尾和 Docker 重启后的恢复行为。
- 确认录播、弹幕和缓存时间轴能够正确关联。

### `PH-002` 自动分析与候选切片

- 增加可配置的滚动分析任务，只处理已完成写入的时间窗口。
- 先实现弹幕密度筛选和字幕分析，再接入模型评分、候选去重及时间范围合并。
- 调用现有 FFmpeg 切片任务生成候选视频，保留评分及推荐理由。
- 通过真实录播回放调节评分阈值，检查漏选、误选和重复切片情况。

### `PH-003` 邮件提醒和部署

- 将切片完成事件接入 Webhook 邮件服务，通知内容包含可访问的视频链接。
- 验证邮件重试、重复事件处理及链接访问权限。
- 在桌面版和 Docker Web 部署中验证完整流程及后台状态展示。

## 8. 验收标准

- `AC-001`：配置的抖音主播开播后可自动开始录制；下播或录制失败时状态可查询。
- `AC-002`：分析任务只读取稳定片段；应用重启后可继续处理，且不会重复生成同一候选。
- `AC-003`：每个生成的候选切片都能追溯到直播、时间范围、评分和推荐理由。
- `AC-004`：切片生成后能够收到邮件；通知中的视频链接可由预期用户访问。
- `AC-005`：AI 或邮件服务异常不会中断直播录制，失败任务可识别并重试。
- `AC-006`：不调用抖音自动投稿接口；发布由用户审核并手动完成。

## 9. 风险与约束

- `RISK-001`：抖音录制依赖账号状态和平台网页接口；接口变化、限流或登录失效可能影响监测与录制，需要监控和恢复机制。
- `RISK-002`：热度评分只是候选排序依据，不能保证作品获得流量；上线前应以实际录播校准阈值。
- `RISK-003`：边录边分析会增加 CPU、磁盘和模型调用成本；应限制分析频率、抽帧数量和单场切片数量。
- `RISK-004`：邮件中的链接必须考虑部署网络和访问控制。项目 Web API 当前没有内置网页登录认证，远程使用应放在 VPN 或带认证的反向代理之后。
- `RISK-005`：自动录制、剪辑和传播应确保拥有相应内容使用权限，并遵守平台规则。
